### Task 1: Fix #48 — Long.compareTo(String) at L9248-9260

**Files:**
- Modify: `converter/flux_gauss.py:9248-9260`

**Root cause:** BinaryOp handler at L9248 early-returns for Long-typed operands BEFORE the String-vs-Numeric coercion at L9262. When left=Long and right=String (quoted literal `'9999'`), `_is_numeric_literal` returns False, so no `Long.valueOf()` wrapping occurs. Result: `vProId.compareTo("9999")` — uncompilable.

**Rust's fix** (`expr.rs` L915-948): Check String FIRST, always wrap non-String side with `String.valueOf(...)`.

**Step 1: Read current code**

Lines 9248-9260:
```python

    cmp_map = {"<": "<", ">": ">", "<=": "<=", ">=": ">=", "=": "==", "<>": "!="}
    if _left_is_primitive or _right_is_primitive:
        if _is_numeric_literal(val.get("right")):
            right = f"((Number) {right}).longValue()" if ".get(" in right else right
        elif _is_numeric_literal(val.get("left")):
            left = f"((Number) {left}).longValue()" if ".get(" in left else left
        return f"{left} {cmp_map[op]} {right}"
    if _is_numeric_literal(val.get("right")):
        right = f"Long.valueOf({right})"
    elif _is_numeric_literal(val.get("left")):
        left = f"Long.valueOf({left})"
    return f"{left}.compareTo({right}) {cmp_map[op]} 0"
```

**Step 2: Add String coercion before the return**

Replace lines 9248-9260 with:


### Task 3: Fix #46 — ascii template at L7851

**Files:**
- Modify: `converter/flux_gauss.py:7851`

**Root cause:** The ascii template `"__EXPR__(int) String.valueOf({args0}).charAt(0)"` uses `String.valueOf(...).charAt(0)` which, when args0 is NOT a String expression (e.g., a Long), calls charAt on the string-representation of the number — semantically wrong. More importantly, the cast `(int)` with a space before `String.valueOf` can be misparsed or produce confusing code.

**Fix:** Change to `String.valueOf({args0}).charAt(0)` and let the numeric cast happen implicitly (char→int is widening, Java auto-converts). Or better: keep the explicit cast but in valid form.

**Step 1: Change L7851**

From:
```python
    "ascii": "__EXPR__(int) String.valueOf({args0}).charAt(0)",
```
To:
```python
    "ascii": "__EXPR__String.valueOf({args0}).charAt(0)",
```

The `__EXPR__` prefix marks this as an expression (already applied). The `.charAt(0)` returns `char` which auto-widens to `int` in Java. No explicit `(int)` cast needed — avoids the double-type-keyword issue. Matching Rust's approach at `expr.rs` L1398.

**Step 2: Verify**

```bash

python3 -m pytest tests/regress/test_issues.py -v -k "TestIssue46" 2>&1 | grep -E "PASS|FAIL|XFAIL|XPASS"
```

Expected: `test_no_double_type_keywords PASSED`

**Step 3: Commit**

```bash
git add converter/flux_gauss.py
git commit -m "fix(#46): remove redundant (int) cast from ascii template

The '(int) String.valueOf(...).charAt(0)' pattern produced confusing
Java with two type keywords adjacent. Java auto-widens char→int, so
the explicit cast is unnecessary. Now 'String.valueOf({args0}).charAt(0)'.

"
```

### Task 4: Fix #47/#49 — Remove id/no/seq→Long heuristic

**Files:**
- Modify: `converter/flux_gauss.py:615-618`

**Root cause:** `_infer_type_from_column_name` at L615 maps column names containing "id", "no", "num", "seq" to `bigint` → Java `Long`. This causes VARCHAR2 variables like `v_pro_id`, `v_step_no`, `v_trade_ids` to be mistyped. The fix: remove this aggressive heuristic — when DDL is unavailable, default to `varchar` (String) instead of guessing Long for name-pattern matches.

**Step 1: Change L615-618**

From:
```python
    if any(s in col for s in ("id", "no", "num", "seq")):
        if "num" in col and "varchar" not in col:
            return "integer"
        return "bigint"
```
To:
```python
    # Removed: aggressive Long heuristic for id/no/seq column names.
    # These caused VARCHAR2 variables to be mistyped as Long (#47, #49).
    # When DDL is unavailable, default to varchar (String) which is safe
    # for both numeric and string ID columns.
```
