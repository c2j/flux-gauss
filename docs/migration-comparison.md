# 存储过程迁移到 Java 方案对比

将数据库存储过程（Oracle PL/SQL、PostgreSQL/OpenGauss PL/pgSQL、SQL Server T-SQL）批量迁移到 Java + MyBatis/Ibatis，是企业数据库架构现代化的典型挑战。本文梳理主流迁移方案，分析各方案的优劣与适用场景，并介绍本项目（FluxGauss）的开发过程与核心优势。

---

## 1. 背景与动机

### 1.1 为什么需要迁移存储过程

企业级系统中，大量业务逻辑以存储过程的形式存在于数据库中。这些存储过程通常积累了数年甚至十余年的业务规则，数量从几十到上万不等。推动迁移的典型场景包括：

- **数据库国产化/换轨**：从 Oracle 迁移到 OpenGauss/GaussDB/PostgreSQL，原有 PL/SQL 不可直接使用
- **架构现代化**：从单体数据库架构演进为微服务架构，业务逻辑需要从数据库层上移到应用层
- **人才稀缺**：精通 PL/pgSQL 或 PL/SQL 的开发人员日益减少，Java 开发团队更易组建
- **可维护性**：存储过程缺乏版本控制、代码审查、CI/CD 等现代开发实践
- **性能扩展**：数据库计算资源昂贵，将计算逻辑迁移到可水平扩展的应用层更经济

### 1.2 核心挑战

存储过程迁移并非简单的"语法翻译"，其核心难点在于：

- **SQL 与过程逻辑交织**：存储过程中 SQL 语句与控制流（IF/FOR/WHILE）、变量声明、异常处理深度耦合
- **数据库方言差异**：PL/SQL、PL/pgSQL、T-SQL 语法和内置函数各不相同
- **类型系统鸿沟**：SQL 类型（NUMERIC、VARCHAR2、REFCURSOR）与 Java 类型系统的映射并非一一对应
- **跨包依赖**：存储过程包之间存在调用关系，迁移时需要保持调用拓扑的正确性
- **动态 SQL**：运行时拼接的 SQL 语句在 Java 中需要用 MyBatis 动态 SQL 或参数化方式重新实现

## 2. 迁移方案分类与对比

### 方案 A：纯手工迁移

由 Java 开发人员逐个阅读存储过程源码，手动编写对应的 Java Service + MyBatis Mapper/XML。

| 维度 | 评价 |
|------|------|
| **优势** | 质量最高，完全可控；开发者能理解业务意图并做合理抽象；适合重构式迁移 |
| **劣势** | 极慢（平均每个存储过程 0.5-2 人天）；质量高度依赖个人能力；难以规模化；人工容易遗漏边界情况（NULL 处理、异常分支）；无一致性保证 |
| **适用场景** | 存储过程数量 < 50 个，且业务逻辑复杂需要重新设计 |
| **效率估算** | 100 个存储过程约需 50-100 人天 |

### 方案 B：AI 大模型逐个迁移

利用 ChatGPT、Claude、GitHub Copilot 等大语言模型，通过对话方式逐个转换存储过程。

| 维度 | 评价 |
|------|------|
| **优势** | 快速原型，单次转换速度快；能处理复杂的自然语言理解；灵活，可根据反馈调整 |
| **劣势** | **无一致性保证**：不同会话、不同 prompt 生成风格不同（某次用 HashMap，某次用强类型）；**上下文丢失**：跨包依赖、类型映射、命名规则需要每次重新说明；**流程碎片化**：需要逐个复制粘贴，无法批量处理；**不可增量**：修改一个存储过程后无法只重新生成受影响的部分；**质量不稳定**：取决于 prompt 质量，复杂的游标循环和 GOTO 逻辑容易出错；**成本**：大批量下 Token 成本可观；**非确定性**：相同输入不能保证相同输出，无法 CI/CD 集成 |
| **适用场景** | 快速验证 POC；少量（< 20 个）复杂存储过程的手动辅助 |
| **效率估算** | 100 个存储过程约需 5-10 天（含人工审核和修正） |

### 方案 C：基于 AST 解析的程序化迁移（FluxGauss 的方法）

使用专用 SQL 解析器将 PL/pgSQL 解析为抽象语法树（AST），然后按照确定的规则系统性地将 AST 节点转换为 Java 代码。

| 维度 | 评价 |
|------|------|
| **优势** | **一致性强**：相同模式产生完全相同的输出；**可大批量处理**：一次转换数百到数万个存储过程；**增量构建**：基于 SHA-256 缓存，只重新生成变更部分；**跨包依赖自动解析**：自动识别包间调用，生成正确的 Service 注入和 import；**类型安全**：从 DDL 解析表结构，精确的 SQL 到 Java 类型映射；**自动化测试生成**：单元测试和集成测试自动生成；**确定性输出**：相同输入永远产生相同输出，可 CI/CD 集成；**源码溯源**：生成的 Java 代码包含原始 SQL 文件名和行号注释 |
| **劣势** | 前期开发投入大（需要开发 SQL 解析器和代码生成器）；对不支持的语法需人工介入（生成 TODO 标记）；解析器对语法错误零容忍（需要先修复 SQL 语法） |
| **适用场景** | 100+ 存储过程的企业级批量迁移 |
| **效率估算** | 开发转换器约需 1-2 个月；转换 100 个存储过程约需 1 小时自动 + 5-10 天人工审核 |

### 方案 D：基于规则/正则匹配的文本替换

使用 sed 脚本、自定义 Python/Shell 脚本，通过正则表达式匹配和替换来完成"转换"。

| 维度 | 评价 |
|------|------|
| **优势** | 实现简单，快速上手；无需额外工具或依赖 |
| **劣势** | **无法理解语义**：正则只能匹配文本模式，不理解 SQL 语法结构；**无法处理嵌套**：IF/FOR/WHILE 的多层嵌套、BEGIN/END 配对对正则是 NP 难问题；**类型推断不可能**：无法从表结构推断变量类型；**跨包依赖不可见**：无法识别包间调用关系；**极易出错**：边界情况（字符串中包含关键字、注释中的代码）无法处理 |
| **适用场景** | 极简单的 SELECT/INSERT 存储过程（< 20 行，无控制流） |
| **效率估算** | 100 个简单存储过程约需 1 天（但质量差，后续返工成本高） |

### 方案 E：商业迁移工具

使用 AWS Schema Conversion Tool、Oracle SQL Developer Migration Workbench、Ispirer MnMTK 等商业工具。

| 维度 | 评价 |
|------|------|
| **优势** | 成熟方案，有技术支持；部分工具支持多种源数据库；可能有图形界面和项目管理功能 |
| **劣势** | **昂贵**：按存储过程数/表数/数据量计费，大规模迁移成本极高；**输出不可控**：生成的代码质量无法保证，通常包含大量冗余或不可读代码；**不支持定制**：无法调整生成风格或命名规则；**厂商锁定**：输出依赖特定框架或运行时；**数据库到数据库**：多数商业工具迁移到另一个数据库（Oracle 到 PostgreSQL），而非迁移到 Java 应用层；**可能不支持 GaussDB/OpenGauss** |
| **适用场景** | 预算充足的大型企业；数据库到数据库的迁移（非存储过程到 Java） |
| **效率估算** | 工具采购和配置约需 1-2 周；实际转换视工具而异 |

## 4. FluxGauss 项目开发历程

### Phase 1：需求分析与技术选型（2026-04）

**背景**：面对大量 OpenGauss/GaussDB 存储过程需要迁移到 Java + MyBatis 的场景，评估了多种技术路线后，选择了基于 AST 解析的程序化转换方案。

**关键决策**：

1. **选择 AST 解析而非正则匹配**：存储过程的嵌套控制流、动态 SQL、游标操作等复杂结构无法用正则可靠处理
2. **选择 Rust 构建 SQL 解析器（ogsql-parser）**：Rust 的模式匹配和数据结构适合构建高可靠性的语法解析器，同时提供 JSON AST 输出供上层消费
3. **选择 Python 实现转换逻辑**：快速迭代，丰富的字符串处理能力，与 JSON AST 交互方便
4. **选择 Spring Boot + MyBatis 作为输出目标**：企业级 Java 技术栈的事实标准，MyBatis 的 XML 映射保留了 SQL 的灵活性

### Phase 2：Python 转换器开发（2026-04 ~ 2026-05）

从零开发 `converter/flux_gauss.py`，最终达到约 13900 行，覆盖了完整的 PL/pgSQL 到 Java 的转换管线。

**主要功能里程碑**：

| 阶段 | 特性 | 时间 |
|------|------|------|
| 基础框架 | AST 解析、过程提取、Service/Mapper/XML 生成 | 2026-04 |
| 控制流转换 | IF/ELSIF/ELSE、FOR-IN-SELECT、WHILE、LOOP | 2026-04 |
| 游标处理 | OPEN/FETCH/CLOSE、REFCURSOR、跨包调用 | 2026-05 |
| 高级语句 | MERGE INTO、TRUNCATE、TABLE OF、FORALL、RETURNING INTO | 2026-05 |
| GOTO 转换 | 状态机模式、do-while + continue 模式 | 2026-05 |
| 内置函数映射 | 50+ SQL 函数（字符串、数学、日期、空值处理、类型转换） | 2026-05 |
| 工程化 | 增量构建、转换报告、SQL 语法校验、断点续做 | 2026-05 |
| 测试生成 | Mockito 单元测试 + Testcontainers 集成测试 | 2026-05 |
| 质量验证 | 6 轮 SQL-Java 等价性对比（V1-V6） | 2026-05 |

**质量验证数据**：

- 48 个 SQL 源文件，其中 36 个包含存储过程
- 生成 36 个 Service 包，357+ 个单元测试全部通过
- 6 轮自动化等价性对比，Python 引擎综合评级 **A-**
- 对比维度覆盖：过程覆盖率、参数映射、DML 等价性、异常处理、游标使用、动态 SQL、源码行号映射

### Phase 3：Rust 转换器重写（2026-05）

为应对 30K 文件级别的超大规模转换需求，使用 Rust 重写了转换引擎（`crates/fluxgauss/`，约 18800 行）。

**架构设计**：

```
Phase 0: 预扫描 DDL        (并行读文件，提取表结构)
Phase 1: 解析 + 提取摘要    (并行调用 ogsql-parser crate)
Phase 2: 全量分析           (顺序执行，跨包依赖需要全量摘要)
Phase 3: 分批生成           (按依赖拓扑排序，批量输出文件)
```

**技术亮点**：

- **三阶段管线**：分离轻量扫描和重量级生成，降低峰值内存
- **ogsql-parser 作为 crate 依赖**：消除 subprocess 调用开销，直接使用 AST 类型
- **Rayon 并行处理**：独立文件的解析和生成并行执行
- **模块化设计**：8 个功能模块（extract、analyze、expr、statement、type_map、naming、config、pipeline），每个模块可独立测试

**当前状态**：通过编译 + 单元测试，综合评级 B+，正在持续追赶 Python 版的功能对齐。

### Phase 4：持续优化（进行中）

- **双引擎交叉验证**：Python 和 Rust 生成结果对比，互相发现转换缺陷
- **对比审计报告**：核心业务包 100% 过程覆盖率，语义等价性验证
- **持续减少 TODO**：从初始的 37 个 TODO 减少到 21 个，逐步覆盖更多 PL/pgSQL 特性

## 5. FluxGauss 核心优势

### 5.1 AST 驱动的语义转换

不是文本替换，不是正则匹配。FluxGauss 通过 ogsql-parser 将 SQL 解析为完整的抽象语法树，然后遍历 AST 节点生成语义等价的 Java 代码。这意味着：

- 嵌套的 IF/FOR/WHILE 能正确转换（正则方案做不到）
- 游标生命周期（OPEN/FETCH/CLOSE）能正确映射为 Mapper 查询
- GOTO 语句能转换为状态机或 do-while 模式
- 动态 SQL 能保留在 MyBatis XML 中而非强行拆解

### 5.2 确定性输出

相同输入永远产生相同输出。这一特性使得：

- 可以将转换器集成到 CI/CD 流水线
- 代码审查可以 diff 生成的差异
- 回归测试有明确的基线

### 5.3 增量构建

基于 SHA-256 内容哈希的缓存机制，配合传递依赖追踪：

- 只重新解析内容变更的 SQL 文件
- 变更文件的调用者也会被重新生成
- 通过 `--resume` 支持断点续做
- 适合大型项目的增量迭代

### 5.4 跨包依赖自动解析

自动识别存储过程包之间的调用关系（如 `pkg_order.create_order(...)` → `orderService.createOrder(...)`），生成正确的：

- Service 注入（`@Autowired`）
- Java import 语句
- 跨包的包名路径解析

### 5.5 类型安全

从 `CREATE TABLE` DDL 解析表结构，构建列类型映射表。配合 `%TYPE` 锚定类型，实现精确的 SQL 到 Java 类型转换：

- `INTEGER` → `int`
- `NUMERIC(18,2)` → `java.math.BigDecimal`
- `VARCHAR2(100)` → `String`
- `employees.salary%TYPE` → 从 DDL 查找实际类型 → `java.math.BigDecimal`
- `REFCURSOR` → `List<Map<String, Object>>`

### 5.6 自动化测试生成

每个存储过程包自动生成两类测试：

| 测试类型 | 框架 | 覆盖范围 |
|----------|------|----------|
| 单元测试 | Mockito + JUnit 5 | 每个 Service 方法的 Mock 调用验证 |
| 集成测试 | Testcontainers / 远程数据库 | 真实数据库上的 SQL 执行验证 |

### 5.7 源码溯源注释

生成的 Java 代码中包含原始 SQL 源文件定位信息：

```java
// Source: PKG_DEPOSIT.sql:38-202 — pkg_deposit.prc_acnt_info_list
public List<Map<String, Object>> prcAcntInfoList(...) { ... }
```

方便开发者在审核时直接定位到原始存储过程，加速人工审核流程。

### 5.8 双引擎验证

Python 和 Rust 两个独立实现的转换器，生成结果可以交叉对比：

- 发现单引擎的转换缺陷
- 提高整体转换可信度
- Rust 引擎为超大规模转换提供性能保障

### 5.9 可扩展性

新增 SQL 函数或语句类型的支持只需修改转换器，一次性覆盖所有输出：

- 添加一个新的 SQL 函数映射：修改函数映射表即可
- 添加新的语句类型支持：新增 dispatch case + handler 函数
- 所有已生成的代码重新运行转换器即可获得更新

### 5.10 企业级工程实践

- **YAML 配置驱动**：支持自定义 Java 包名映射、多种日志框架、数据库连接配置
- **骨架文件保护**：`pom.xml`、`application.yml` 等骨架文件只在不存时生成，避免覆盖手动调整
- **转换报告**：自动生成 Markdown 格式的转换报告，记录映射关系、跳过项、错误信息
- **SQL 语法预校验**：在转换前校验 SQL 语法，提前发现问题

## 6. 结论与建议

### 按规模选择方案

| 存储过程规模 | 推荐方案 | 理由 |
|-------------|----------|------|
| < 50 个 | 手工迁移 + AI 辅助审核 | 规模小，手工可控；AI 可加速理解 |
| 50 - 200 个 | AST 程序化迁移（FluxGauss） | 规模适中，自动化收益明显 |
| 200 - 1000 个 | AST 程序化迁移 + 分批迁移 + 人工审核 | 需要增量构建和自动化测试 |
| 1000+ 个 | AST 程序化迁移（Rust 引擎）+ 完整 CI/CD | 需要 Rust 引擎的性能优势 |

### FluxGauss 特别适合的场景

- 源数据库：OpenGauss / GaussDB / PostgreSQL
- 目标架构：Spring Boot + MyBatis（或 Ibatis）
- 存储过程特征：包含复杂控制流、游标操作、跨包调用、动态 SQL
- 项目需求：需要批量处理、增量迭代、自动化测试、可追溯性

### FluxGauss 的局限

- 当前仅支持 OpenGauss/PostgreSQL 方言（不直接支持 Oracle PL/SQL 或 SQL Server T-SQL，需先完成数据库迁移到 PostgreSQL 系）
- 复杂动态 SQL（运行时拼接表名、列名）仍需人工处理
- 部分高级特性（管道函数、DBE_SCHEDULER）生成 TODO 标记，需人工补全
- Rust 引擎功能尚在对齐 Python 引擎过程中
